# review-agent

Outil local (WSL) qui pilote Claude Code sur le travail GitLab : tickets assignés, agent dev (ticket vers MR Draft) et review des MR des collègues. Le support Planio arrivera ensuite. Il n'est pas déployé : chaque utilisateur le clone et le configure pour lui.

## Repères

- Fonctionnement, sécurité et choix techniques : `docs/architecture.md`.
- Backlog : `docs/roadmap.md`. Quand un item est terminé, mets à jour sa ligne dans le tableau « Vue d'ensemble » et ajoute un paragraphe **Implémenté (date)** dans sa section : ce qui a été fait, où, ce qui a été testé, les limites connues.
- Node 24, TypeScript strict, ESM (`NodeNext` : imports relatifs en `.js`), exécution via `tsx`.
- Base de données : SQLite local (`data/`, non versionné) ou PostgreSQL (`DATABASE_URL`), derrière l'interface asynchrone `Db` (`src/db/db.ts`). Le SQL des dépôts est **commun aux deux moteurs** : paramètres `?`, `ON CONFLICT ... RETURNING id`, `CAST(COUNT(*) AS INTEGER)`, alias en snake_case, jamais de fonction propre à un moteur (`datetime('now')`, `strftime`...) : utiliser `db.sql`. Toute méthode de dépôt est asynchrone et doit être attendue (`await`) : TypeScript ne signale ni un appel oublié, ni `{ ...promesse }`. Les migrations sont dans `migrationsFor` (`src/db/migrations.ts`), appliquées au démarrage. Ne jamais modifier une migration déjà appliquée : en ajouter une à la fin. Tout changement de schéma ou de requête se teste sur les deux moteurs (`src/db/db.test.ts`, et `TEST_DATABASE_URL` pour un vrai serveur PostgreSQL).
- Cible à long terme (plateforme hébergée, conteneur par utilisateur) : `docs/vision-plateforme.md` et `docs/parcours-utilisateur.md`. Spec seulement, rien n'est implémenté. Les décisions de sécurité qui y sont prises (patch seul hors du conteneur, caviardage des données clients avant tout prompt) s'appliquent à toute évolution vers cette cible.

## Commandes

- `npm run typecheck` et `npm test` avant de considérer une modification terminée.
- `npm run review:once -- <url de la MR>` pour tester une review sans rien poster.
- `npx tsx scripts/smoke-review.ts` et `npx tsx scripts/smoke-dev.ts` après toute modification des options de la CLI `claude` (tests réels, quelques centimes de quota).
- Dans WSL, lancer `npm` et `npx` depuis un shell qui a le Node de WSL dans son PATH (`bash -lc`), sinon c'est le npm de Windows qui répond.
- `tsx watch` ne voit pas toujours les fichiers modifiés depuis Windows : après un changement de code serveur, vérifier que le serveur a bien redémarré (heure du processus) et sinon le relancer à la main. Ne pas modifier le code serveur pendant qu'une tâche d'agent tourne : le redémarrage la coupe.

## Règles du projet

- Code et textes en français pour les messages, logs et commentaires. Identifiants en anglais.
- Rien en dur qui dépende de l'utilisateur, de l'entreprise ou du projet (URL internes, noms de projets, labels, stacks, consignes) : URL et token dans le `.env`, tout le reste dans les réglages du dashboard (`src/settings/`), validés par zod côté serveur. Les prompts `prompts/*-system.md` restent génériques : ce sont les valeurs par défaut, remplaçables dans Paramètres > Prompts de base. Les consignes perso vont dans Paramètres > Consignes des agents.
- Les garde-fous des prompts (`prompts/*-guardrails.md` : anti-injection, ticket non autoritaire, pas de commit ni de push par l'agent, format de réponse) sont toujours ajoutés en dernier par `src/prompts.ts` et ne doivent jamais devenir modifiables depuis le dashboard.
- Les décisions d'agir (commenter, approuver, pousser, créer une MR, répondre à un client) restent dans du code déterministe et testé, jamais dans la sortie du modèle seule.
- **Fusion de la pièce** (`src/dev/merge.ts`, `src/dev/pieceRoutes.ts`) : l'outil peut fusionner la MR de l'agent dev, mais seulement sur un clic confirmé d'une personne, jamais depuis la sortie du modèle, et seulement si `mergeReadiness` le permet : MR ouverte, de la branche de la tâche vers la branche cible réglée du projet, review de l'agent terminée sans point à analyser **sur le commit de tête actuel**, CI sans rouge ni en cours. Le serveur recalcule tout depuis la forge à chaque demande (l'interface ne décide rien), et la fusion est conditionnée au commit relu (`sha`). La review de sa propre MR ne publie ni n'approuve jamais seule. L'outil ne déploie rien. Ne jamais assouplir ces règles ni ajouter de fusion automatique sans demande explicite.
- **Push** : uniquement la branche créée pour le ticket, via `assertBranchAllowed` (`src/dev/guard.ts`), sans `--force`, MR toujours en Draft. Ne jamais affaiblir ces garde-fous sans demande explicite.
- **Reprise d'une MR** (`runFollowup`, `src/dev/pipeline.ts`) : même branche, nouveau commit poussé en fast-forward, jamais de `--force`. Elle refuse d'écraser un dossier de travail contenant des modifications ou des commits non poussés. Tout changement de ce flux se teste avec le test d'intégration git local (`src/review/workspace.test.ts`).
- **Agent dev sur un dépôt en ISO-8859-1 (ex. sra-moteur)** : déconseillé. `src/dev/fileGuard.ts` refuse le push d'un fichier corrompu, mais l'agent ne sait pas réparer (roadmap, item 35).
- **Espaces** : reviews, tâches, projets, réglages, coûts et secrets appartiennent à un espace (`workspace_id`). Les dépôts (`createReviewRepo(db, workspaceId)`...) sont liés à un espace, toute requête sur ces tables nomme `workspace_id`, et aucun SQL sur elles ne s'écrit hors des dépôts. Un test d'audit (`src/db/isolation.test.ts`) lit le code et échoue sinon ; toute nouvelle méthode de dépôt s'ajoute aussi aux tests d'étanchéité avec deux espaces.
- **Personnes** : le code des pipelines et du serveur ne tient jamais de dépôt ni de connexion de forge global. Il reçoit ceux de la personne servie (`TenantDeps`, `src/tenants/`), construits depuis SON coffre. Le `.env` ne sert que le propriétaire. Toute nouvelle fonction qui touche une forge ou une donnée doit marcher pour deux personnes à la fois (voir `src/tenants/tenants.test.ts`).
- **Audit** : toute écriture sur une forge passe par le connecteur ou par `RepoWorkspace.pushBranch`, enveloppés par `auditConnector` et `auditWorkspace` (`src/connectors/audited.ts`). Une nouvelle méthode d'écriture d'un connecteur s'ajoute à `CONNECTOR_WRITES` et à `src/connectors/audited.test.ts`.
- **Connecteurs** (`src/connectors/`) : les pipelines, le poller, le serveur et les CLI n'utilisent que l'interface `ForgeConnector` et ses types neutres. Les types et le client GitLab (`src/gitlab/`) ne sortent pas de `src/connectors/gitlab.ts`. Un détail propre à une forge (URL, référence git, identifiants) va dans le connecteur, jamais dans un pipeline. Toute review, tâche de dev et réglage de projet porte sa forge (colonne `source`) : un pipeline retrouve la sienne par `deps.forges.get(row.source)`, jamais par un connecteur unique, car deux forges peuvent donner le même numéro de projet ou de ticket. Tout nouveau chemin qui lit ou écrit chez une forge se teste avec deux forges (`src/connectors/routing.test.ts`). `src/testing/` (faux connecteur, harnais) est réservé aux tests : ne jamais le brancher sur un script ou le dashboard.
- **Exécuteur d'agent** (`src/agent/cliRunner.ts`) : les protections d'isolation (`--safe-mode`, `--strict-mcp-config`, `dontAsk`, MCP interdit) sont écrites dans l'exécuteur, jamais dans la requête. Ne jamais les rendre paramétrables. `src/agent/cliRunner.test.ts` (faux binaire `claude`) doit échouer si l'une d'elles disparaît.
- **Contrôle des fichiers avant push** (`src/dev/fileGuard.ts`) : ne pas l'affaiblir. Il sera la base du contrôle des patchs venant d'un conteneur (`docs/roadmap-plateforme.md`, D5).
- Les agents passent par la CLI `claude -p`, sur l'abonnement de l'utilisateur par défaut, ou avec `ANTHROPIC_API_KEY` si le réglage « Connexion à Claude » est sur « Clé API » (`createRunner`, `src/agent/index.ts`). La clé n'est lue que dans `config.anthropicApiKey`, transmise uniquement dans ce mode, masquée dans les erreurs et le journal : ne jamais l'afficher, la journaliser ni la renvoyer par l'API (le dashboard ne reçoit que sa présence). En mode abonnement, toute clé du shell est écartée. Modèle plafonné à `claude-sonnet-5-5` en effort `high` : ne jamais relever ce plafond sans demande explicite.
- **Conteneurs partout** (décidé le 2026-11-19) : `AGENT_RUNTIME` vaut `docker` par défaut et `host` est refusé au démarrage dès qu'une connexion par compte est configurée (`src/config.ts`). Ne jamais ajouter de repli sur la machine (une tâche sans identifiants Claude est refusée, pas lancée sur l'hôte), ne jamais monter le dossier personnel de la machine (`~/.claude`) dans un conteneur, ne jamais donner à un conteneur la clé API **et** le jeton d'abonnement (la clé passerait devant l'abonnement). Le jeton d'abonnement (`claude setup-token`) est propre à la personne (coffre, `config.claudeOauthToken`), transmis par l'environnement du client `docker` et jamais dans les arguments, masqué comme la clé API ; un membre n'hérite jamais de celui du propriétaire. Les tests qui lancent un faux `claude` sur la machine fixent `AGENT_RUNTIME: "host"` explicitement.
- Droits des agents :
  - review : lecture seule ;
  - dev : lecture/écriture du worktree, git en lecture, commandes autorisées du projet ;
  - les deux : `--safe-mode`, `--strict-mcp-config`, `dontAsk`, pas de réseau.

  Tout élargissement de ces droits doit être discuté avant.
- **Salles du monde de la forge** (`public/rooms/*.json`, `src/rooms/`) : des données, jamais du code. Une salle ne peut contenir que ce que `src/rooms/catalog.ts` permet (objets, thèmes, apparences) et doit passer `npx tsx scripts/check-rooms.ts`. Ne jamais afficher un texte de salle en HTML (le jeu utilise `textContent`) ni ajouter un champ qui exécute quelque chose. Format : `docs/salles.md`.
- **Pièces jointes** (`src/attachments/`) : captures, maquettes et données de la personne, jamais un contenu de confiance. Types et contenu contrôlés par `rules.ts` (pas de svg, html ni exécutable), fichiers rangés par espace sans table, identifiants validés avant tout chemin. L'agent dev les lit dans `.ra-attachments/` du dossier de travail : ils sont supprimés dès qu'il a fini et `commitAgentWork` refuse tout commit qui en contient. Ne jamais les committer, ne jamais donner à l'agent un accès hors de son dossier de travail pour les lire, ne jamais en faire des instructions.
- **Arène et caractéristiques** (`public/forge/combat.js`, `arena.js`, `docs/arene.md`) : logique pure, déterministe, tout dans le navigateur ; ne jamais en tirer d'XP, de butin rare ou de classement tant que la progression est falsifiable (navigateur). Une arme ou une rareté ajoutée au butin (`src/game/loot.ts`) doit avoir son profil de combat : `src/rooms/combat.test.ts` échoue sinon. Une arme du butin est unique : ses valeurs viennent de `rollWeapon` (`combat.js`), calculées depuis (type, rareté, graine de l'événement), jamais tirées au hasard ni stockées côté navigateur. La salle `arene` est livrée dans `public/rooms/` et le jeu retrouve son Maître d'armes par identifiant (`ARENA_ROOM`, `ARENA_MASTER`). Tout calque qui capture le clavier doit se fermer quand on quitte l'onglet de la forge (`pause`).
- **La forge (jeu) est isolée du noyau et éteignable** : rien hors de `src/game/` et `src/rooms/` ne l'importe (sauf l'appel `registerGame` de `app.ts`), toutes ses routes sont dans `src/game/routes.ts` (404 quand le drapeau `game.enabled` est éteint, seul `/api/game` reste joignable), et ses réglages vivent dans la section `game` du magasin de réglages (`src/game/prefs.ts`), jamais dans les réglages de projet. **Une fonctionnalité réelle (ticket, agent dev, review, fusion, Scribe) ne dépend jamais du jeu et n'est jamais accessible seulement par lui** : elle a sa page dans le tableau de bord, la forge n'est qu'une porte de plus. Un test de `src/server/gameFlag.test.ts` doit échouer si une route du jeu répond quand elle est éteinte.
- **Droits par rôle** (`src/auth/permissions.ts`) : chaque route de l'API demande un niveau (`read` : tous, lecteur compris ; `act` : membre et administrateur ; `admin` : administrateur seulement), contrôlé dans UN crochet de `app.ts` à partir d'UNE table. **Toute nouvelle route `/api/...` se classe dans cette table** : une route non classée est refusée à tout le monde (même à l'administrateur), et `permissions.test.ts` échoue dans les deux sens (route sans niveau, niveau sans route). Une écriture n'est jamais `read` (seule exception : changer d'espace, qui ne touche que la session). Régler l'espace (réglages, projets et leurs commandes autorisées, équipe, journal, quotas) est `admin`. L'interface grise ce que le rôle ne permet pas, mais ne décide rien : le serveur reste seul juge.
- **Équipe et invitations** (`src/team/`, `src/db/invitations.ts`, `src/auth/login.ts`) : une invitation est un jeton de 256 bits à usage unique, qui expire, révocable ; seule son empreinte SHA-256 est en base, le lien n'est montré qu'une fois à la création, et il n'apparaît dans aucune liste ni journal. Elle ne se consomme que si la personne n'est pas déjà membre, en UNE instruction (de deux arrivées simultanées, une seule entre), et l'invitation décide du rôle : un vieux lien ne promeut jamais un membre. Les pages `/invite/...` échappent tout texte saisi par un autre, ne se mettent pas en cache et n'envoient pas de référent. Retirer un membre ferme ses sessions de cet espace, arrête ses détecteurs et efface ses jetons de cet espace. L'espace garde toujours un administrateur.
- **Quotas par personne** (`src/budget.ts`, `src/db/costs.ts`) : le propriétaire d'une review ou d'une tâche est la personne dont le dépôt la crée (`createReviewRepo(db, ws, userId)`, `createDevTaskRepo(db, ws, userId)`) : tout nouveau chemin qui en crée doit passer le bon `userId`. Le contrôle (`assertQuotaAvailable`) est fait au lancement par l'API (refus immédiat, 429, rien de créé) ET au démarrage de la file (les reviews détectées toutes seules passent aussi par là). Budget en dollars : mode clé API seulement ; agents par jour : les deux modes. 0 = sans limite, null = valeur de l'espace.
- **Connexion par email** (`src/auth/password.ts`, `passwordLogin.ts`, `passwordRoutes.ts`, `pages.ts`, `src/mail/`, `src/db/credentials.ts`, `emailTokens.ts`) : active seulement si `RESEND_API_KEY` et `MAIL_FROM` sont renseignés (c'est l'email qui prouve l'adresse). Aucun compte n'est créé sans que la personne ait ouvert un lien reçu à son adresse : pas de compte « en attente », donc pas de prise de compte à l'avance. Mots de passe en scrypt (empreinte lente, sel propre), table `credentials` séparée de `users` (jamais remontée par un `SELECT *`), de 10 à 200 caractères, aucune règle de composition. Liens d'inscription et de nouveau mot de passe : jeton de 256 bits, empreinte seule en base, usage unique atomique (`consume`), 60 minutes, un nouveau lien annule le précédent ; un mot de passe refusé ne brûle pas le lien. Connexion, inscription et « mot de passe oublié » répondent pareil que l'adresse existe ou non (et dépensent le même temps) ; seuls les comptes qui ont un mot de passe reçoivent un lien de nouveau mot de passe (un compte de forge n'en a pas : sinon l'adresse non confirmée d'une forge prendrait le compte). Un nouveau mot de passe ferme toutes les sessions du compte. Les liens des emails se construisent avec `PUBLIC_URL`, jamais avec l'en-tête `Host`. Limites : 10 essais par adresse et par 15 minutes, 10 demandes d'email par IP et par heure, 3 par adresse et par heure, 3 invitations par adresse et par jour, 20 par administrateur et par heure. Les formulaires des pages publiques passent par `/auth/form.js` (JSON avec l'en-tête `x-review-agent`) : l'anti-CSRF n'a aucune exception.
- **Organisations et invitations par email** : toute personne connectée crée des organisations (espaces d'équipe, 10 au plus, `POST /api/workspaces`) et en est l'administrateur ; elle y invite par email. Une invitation par email vise une adresse, son lien part à cette adresse seulement et n'est JAMAIS renvoyé à l'administrateur (c'est ce qui fait de sa lecture une preuve de l'adresse) ; si l'email ne part pas, l'invitation est révoquée aussitôt. Elle s'accepte par mot de passe (création du compte, ou connexion) ou d'un clic quand on est déjà connecté avec un compte qui a cette adresse ET un mot de passe ; jamais par une forge. Toute personne a un espace personnel, invitée ou non. `AUTH_SIGNUP=invite` (défaut) n'empêche pas un invité de créer sa propre organisation et d'y inviter d'autres personnes : la maîtrise des ressources passe par les quotas.
- **Limitation de débit** (`src/auth/rateLimit.ts`) : la connexion, son retour et les invitations sont limités par adresse IP (30 par 10 minutes). `TRUST_PROXY=true` seulement derrière un reverse proxy, sinon l'adresse serait falsifiable.
- **Scribe** (`src/scribe/`) : l'agent n'a AUCUN outil (`--tools ""`, dossier temporaire vide) et ne renvoie qu'un brouillon. Il ne crée jamais rien : le ticket ou le projet est créé par le code (`createTicket`, `createProject` du connecteur, donc audités) après la validation de la personne et `clean.ts`, sous un plafond horaire. Ne jamais lui donner d'outil, ni lancer une création depuis sa seule sortie. Le texte du Scribe (`prompts/scribe-*.md`) suit les mêmes règles que les autres prompts : garde-fous non modifiables.
- Tout contenu venant de GitLab ou Planio (descriptions, tickets, commits, sortie du modèle) est non fiable : il est balisé dans les prompts et échappé dans le dashboard.
- Ne jamais lire ni modifier le `.env`. La configuration attendue est documentée dans `.env.example`.
- Git : ne jamais push ce dépôt sans demande explicite dans le même message, pas de trailer `Co-Authored-By`. Pas d'action réelle sur GitLab ou Planio (commentaire, approbation, push, MR) pendant le développement sans accord : tester avec `review:once` ou un dépôt local.
- « Note dans le backlog » : documenter l'item dans la roadmap, sans rien implémenter avant le feu vert.
- Rédaction : pas de tiret cadratin (utiliser points, virgules, deux-points).

## Méthode de travail (inspirée du Spec-Driven Development)

Le niveau de cérémonie dépend de la taille du changement :

- **Petit fix ou changement bien cadré** : coder directement, puis typecheck, tests et résumé.
- **Fonctionnalité moyenne ou grosse** (nouvelle action sur GitLab, nouveaux droits d'agent, nouvelle table, nouveau flux) : suivre ces étapes avant de coder.

1. **Spécifier** : reformuler le besoin en *quoi* et *pourquoi* (déclencheur, cas nominal, cas limites), sans parler technique.
2. **Clarifier** : lister les zones floues et poser les questions avant de coder. Ne jamais deviner une règle de workflow (labels, branches cibles, quand approuver) : la noter « à trancher » dans la roadmap.
3. **Planifier** : fichiers touchés, migration éventuelle (`src/db/index.ts`), réglages à exposer dans le dashboard, impact sur les garde-fous.
4. **Découper** en tâches courtes et vérifiables une par une.
5. **Analyser** : relire spec, plan et tâches ensemble (rien d'oublié, rien de hors-scope, aucun garde-fou affaibli).
6. **Implémenter et vérifier** : tests sur la logique pure et les garde-fous, test d'intégration git local pour tout ce qui pousse, smoke tests si les options `claude` changent.
7. **Documenter** : roadmap (« Implémenté (date) ») et `docs/architecture.md` si le flux change. Dire honnêtement ce qui n'a pas été testé contre le vrai GitLab.

Même logique pour les agents de l'outil : un ticket trop flou doit faire répondre l'agent dev en `blocked` avec ses questions, plutôt que coder au hasard.
